# Describe methods to evaluate FM performance

Choosing and keeping a foundation model (FM) requires evidence that it works. This task covers how to evaluate FMs and the applications built on them, which metrics fit which job, and how to connect model quality to business results. Expect scenario questions that ask you to match an evaluation method or metric to a stated need.

## Key concepts

### Approaches to evaluating an FM

- **Benchmark datasets** are standard prompt sets, often with reference answers, that let you score many models the same way. Results are repeatable and comparable, but they measure general ability, not your specific task.
- **Custom prompt datasets** are built from your own real examples (with expected answers). They test the work your business actually needs.
- **Human-in-the-loop evaluation** uses people, such as employees or subject-matter experts, to rate or compare responses. It is best for subjective qualities such as tone, but it is slower and costlier.
- **Amazon Bedrock Model Evaluation** runs three job types: programmatic (automatic) jobs with built-in or custom datasets, jobs that use a **judge model** (LLM-as-a-judge), and jobs that use human workers. Amazon SageMaker Clarify offers similar model evaluation jobs for JumpStart models.

### Metrics for FM performance

- **ROUGE** (Recall-Oriented Understudy for Gisting Evaluation) counts overlap between generated and reference text, with a recall focus. It is typical for summarization.
- **BLEU** (Bilingual Evaluation Understudy) measures n-gram precision against reference translations. It is typical for machine translation.
- **BERTScore** compares contextual embeddings, so it measures semantic similarity and tolerates paraphrase better than ROUGE or BLEU.
- **LLM-as-a-judge** has a second model score each response and explain the score. Built-in Bedrock judge metrics include correctness, completeness, faithfulness, helpfulness, logical coherence, relevance, following instructions, professional style and tone, harmfulness, stereotyping and refusal. You can also define custom metrics.

ROUGE, BLEU and BERTScore need reference text. A judge model can also assess qualities with no single right answer.

### Does the FM meet business objectives?

Model scores are not outcomes. Compare real results with a baseline: time saved for **productivity**, session length and return visits for **user engagement**, and success on the actual work for **task fit**. A model that tops a public benchmark may still fail your tasks, so test with your own data.

### Evaluating applications built with FMs

Applications are more than one model call, so evaluate the parts and the whole.

- **RAG:** Bedrock RAG evaluations score both retrieval and generated answers, using queries with ground truth for the expected text and responses.
- **Agents:** Amazon Bedrock AgentCore Evaluations scores agent behavior with built-in and custom evaluators using LLM-as-a-judge techniques. AgentCore Observability traces each step and reports metrics such as latency, token usage and errors in Amazon CloudWatch.
- **Workflows:** Check each step and the end-to-end result so you can find which stage introduces errors.

### Business objective alignment metrics

- **Task completion rate:** the share of requests successfully completed.
- **User satisfaction:** ratings or feedback from users.
- **Cost per interaction:** what each conversation or request costs to serve.

Define targets for these before evaluating. When models perform alike, the stated business goal decides.

## Key terms

| Term                 | Meaning                                                           |
| -------------------- | ----------------------------------------------------------------- |
| Benchmark dataset    | Standard prompts and references used to score models consistently |
| Ground truth         | The expected answer or retrieved text used for scoring            |
| ROUGE                | Recall-oriented overlap metric, used for summaries                |
| BLEU                 | Precision-oriented n-gram metric, used for translation            |
| BERTScore            | Embedding-based semantic similarity metric                        |
| LLM-as-a-judge       | A second LLM scores and explains responses                        |
| Faithfulness         | Whether a response sticks to the supplied context                 |
| Task completion rate | Percentage of requests an application resolves                    |

## Comparisons

| Need                                 | Best fit                                            |
| ------------------------------------ | --------------------------------------------------- |
| Compare models on a shared standard  | Benchmark dataset                                   |
| Judge subjective tone or brand voice | Human evaluation, or judge model with custom metric |
| Scale scoring with explanations      | LLM-as-a-judge                                      |
| Summarization coverage               | ROUGE                                               |
| Translation precision                | BLEU                                                |
| Meaning despite different wording    | BERTScore                                           |
| Retrieval plus answer quality        | Bedrock RAG evaluation                              |
| Agent quality and step traces        | AgentCore Evaluations and Observability             |

## Exam tips

- Match the metric to the task: ROUGE for summaries, BLEU for translation, BERTScore for meaning.
- Technical metrics (ROUGE, perplexity, parameter count) are not business metrics. Business answers mention completion rate, satisfaction, cost, productivity or engagement.
- Subjective quality points to humans or a judge model, not overlap metrics.
- For RAG, evaluate retrieval and generation. For agents, think AgentCore Evaluations and Observability.
- Public benchmark success does not prove fit for your own task; use custom data.
